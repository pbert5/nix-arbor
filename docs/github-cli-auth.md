# GitHub CLI authentication on the server

Git configuration for `ash` is generated by Home Manager.  The GitHub CLI
credential helper is therefore configured in `config/users/default.nix`, for
both `https://github.com` and `https://gist.github.com`.  Each host has an
empty helper followed by:

```text
!<nix-store-path-to-gh> auth git-credential
```

The empty helper resets any previously configured helper for that host, while
the second entry invokes the `gh` executable from the evaluated Nix package.
Git asks `gh` for the active credential at runtime; no token is present in Nix
source, the lock file, the store, or Git configuration.

After deployment, authenticate interactively with `gh auth login`.  That login
only needs to persist GitHub CLI's own mutable state; it does not need to edit
the Home Manager-owned Git configuration.  A read-only check is:

```sh
git config --global --get-all credential.https://github.com.helper
```

## Credential storage audit

Current GitHub CLI on Linux uses the Secret Service D-Bus API through its
`go-keyring` dependency.  A desktop environment is not strictly required,
but a working per-user D-Bus session and an unlocked Secret Service provider
(commonly GNOME Keyring) are required.  An SSH login on this server does not
provide that lifecycle reliably, and enabling GNOME Keyring would add a
session-dependent service without making non-interactive SSH use robust.

Consequently this profile does not enable a keyring stack by default.  The
simple server architecture is to keep `gh auth login` as an interactive,
per-user operation and verify that the host has a usable Secret Service
session before relying on secure storage.  If no such session exists, `gh`
falls back to its plaintext host configuration; operators should treat that
as an explicit security decision and remove or migrate the stored credential
before using the host for sensitive work.  A future keyring deployment would
need to be designed together with user-session startup, keyring unlocking, and
SSH/non-interactive behavior; installing only a package is insufficient.

## Codex execution recovery

The repository preflight checks `gh auth status` without reading or printing a
token. If ordinary authenticated `gh` access fails during a Codex session:

1. Try `gh auth token` interactively and keep its output out of logs, files,
   prompts, and comments. Never print or store the token as part of setup.
2. Ensure the Codex session has the required network capability, then pass the
   token only to the intended command, for example:

   ```sh
   GH_TOKEN="$(gh auth token)" gh issue view 1 --repo pbert5/nix-arbor
   ```

   The command substitution is intentionally per-command and must not be
   exported or persisted.
3. Verify the intended read or mutation immediately afterward. For an
   unexpected authenticated 404, first try a parent/list/search query before
   concluding that the issue or repository is absent.

`scripts/codex-preflight --require-github` turns missing or failed GitHub CLI
authentication into `NOT_READY`; without that flag it is reported as a
recommendation for local, read-only work. The preflight does not attempt login,
change credential helpers, enable network access, or repair authentication.
